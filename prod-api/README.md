# prod-api

A small, intentionally imperfect records API used for a production-readiness
engineering exercise. It is a real, runnable TypeScript service, not a mock:
the starter is buildable and testable, but it is **not production-ready**.

The service exposes synthetic records from an in-memory array. It does not use
a database, an external service, cloud credentials, or any runtime network calls
beyond its own HTTP listener.

## Stack

- Node.js 20.11 or newer
- TypeScript in strict mode
- [Hono](https://hono.dev/) with `@hono/node-server`
- Node's built-in test runner, executed through `tsx`
- `dotenv` for loading a local `.env` file

## Install and run

From the project root:

```bash
npm ci
cp .env.example .env
npm test
npm run build
npm start
```

The service listens on `http://127.0.0.1:3000` with the example environment.

For an auto-restarting development process:

```bash
npm run dev
```

For static type checking without emitting files:

```bash
npm run typecheck
```

All environment variables are optional. The `.env` file only provides local
example values; the service falls back to the defaults documented below when it
is absent. Do not commit `.env` or add real credentials to `.env.example`.

## API

### `GET /health`

Returns process uptime and a records availability check in one response. The
endpoint currently reports HTTP `200` while the process can answer requests.

```json
{
  "status": "ok",
  "service": "records-api",
  "uptimeSeconds": 12,
  "checks": {
    "records": "ok"
  }
}
```

### `GET /records`

Returns a page of synthetic records. Both query parameters are optional.

| Parameter | Default | Current behavior |
| --- | --- | --- |
| `limit` | `DEFAULT_PAGE_SIZE` | Number of records to return |
| `offset` | `0` | Number of matching records to skip |

```bash
curl 'http://127.0.0.1:3000/records?limit=2&offset=0'
```

```json
{
  "data": [
    {
      "id": "rec_001",
      "name": "Quarterly access review",
      "owner": "Security",
      "status": "active",
      "updatedAt": "2026-09-18T14:05:00.000Z"
    },
    {
      "id": "rec_002",
      "name": "Checkout latency investigation",
      "owner": "Storefront",
      "status": "active",
      "updatedAt": "2026-09-22T08:40:00.000Z"
    }
  ],
  "meta": {
    "total": 6,
    "limit": 2,
    "offset": 0
  }
}
```

### `GET /records/:id`

Returns one record.

```bash
curl 'http://127.0.0.1:3000/records/rec_001'
```

```json
{
  "data": {
    "id": "rec_001",
    "name": "Quarterly access review",
    "owner": "Security",
    "status": "active",
    "updatedAt": "2026-09-18T14:05:00.000Z"
  }
}
```

The records are deliberately in memory. They are identical on every start,
there is no write endpoint, and the data is not shared between processes.

## Configuration

| Variable | Default | Intended meaning |
| --- | --- | --- |
| `NODE_ENV` | `development` | Runtime environment |
| `HOST` | `127.0.0.1` | Interface to bind |
| `PORT` | `3000` | TCP port to bind |
| `DEFAULT_PAGE_SIZE` | `20` | Page size when `limit` is omitted |
| `MAX_PAGE_SIZE` | `100` | Maximum allowed page size |

The values in `.env.example` are safe local placeholders only.

## Tests

```bash
npm test
```

Tests use Hono's `app.request()` helper and do not bind a network port. They can
be extended with additional route, configuration, and health-check cases. The
test command is an npm script, so it is the canonical way to run the suite.

## Exercise brief

This starter contains production-readiness gaps. The bounded target for a
focused engineering session is:

1. Make configuration fail fast and internally consistent, including limits
   that the request path actually honors.
2. Validate record-list query input completely and put all API client errors
   behind one documented JSON error contract.
3. Separate liveness from readiness and make the not-ready state reproducible
   in local tests.
4. Add deterministic, offline failure-path tests for the above behavior.

Safe logging and deployment assumptions are evidence checks in the readiness
checklist; they are not an invitation to add persistence, authentication, rate
limiting, cloud infrastructure, or new product features. No deployment or cloud
credentials are required to complete the exercise.

Do not treat the current tests or documentation as verification. Record actual
commands and observations in
[docs/readiness-checklist.md](docs/readiness-checklist.md), and update this
README when API behavior changes.
